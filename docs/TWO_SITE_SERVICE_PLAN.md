# 수경재배 + Y-farm 단일 서비스 통합 기획

작성: 2026-11-03. 기획 및 구현 상태를 함께 기록한다. 현재 로컬 코드에 백엔드·웹 UI의 2-site 통합을 반영 중이며, 장비 접속·급수 시험·배포는 하지 않았다.

## 1. 확인된 현 상태와 기준

- 백엔드 `Plant`/`Order`에 재배 공간 구분이 없다. `Plant`의 영상 배정은 `rdkCameraId`·`rdkZone`에 묶여 있고, 식물 상세의 `streamingUrl` 발급 및 스트림 프록시는 RDK 전용이다. 따라서 Y-farm 식물에 같은 필드를 재사용하면 두 게이트웨이의 카메라 ID가 충돌할 수 있다.
- 기존 수경재배는 RDK X5의 C110 4대와 카메라당 6×3 영역을 사용한다. `docs/PHYSICAL_CAMERA_LAYOUT.md`의 실물 배치와 기존 식물·영상 할당을 보존한다.
- 기획 착수 전 백엔드에는 `POST /api/web/control/water`, `GET /api/rdk/command/:plantId`, `POST /api/rdk/water`가 있었고, 그때는 사이트 검사와 Pi 전용 인증이 없었다. 현재 로컬 백엔드에는 Y-Farm Pi 전용 API가 추가됐지만 Pi agent 코드는 아직 새 API를 호출하지 않는다. `GET /api/rdk/command/:plantId`는 현재 사용 중단(`410`)이다.
- 프론트 실시간 페이지는 `streamingUrl`을 사용하고 성장 기록 버튼만 있다. `Plant` 타입에 재배 공간과 급수 가능 여부가 없으며, 관리자 화면은 주문·카메라 노드를 수경재배 중심으로 표시한다.
- `Desktop/RasberryPi/README.md` 기준 수동 서보 제어는 GPIO18, 활성 사출구 **1·3·4·5·6·7·8·9**, CN0023 펄스 **500~2500µs**, 1번 영점 −90°, 개별 보정(3:+8°, 4:+5°, 5:+10°)을 쓴다. Pi 자동 실행기(`irrigation/irrigation_agent.py`)는 GPIO18을 직접 열고 outletIndex 0~9/1000~2000µs를 사용하며 보정 파일을 공유하지 않는다. 별도 systemd 예제는 servo GUI와 충돌 선언이 있으나 실기 service 상태는 이번 점검에서 확인하지 않았다. 그대로 새 backend에 연결하거나 활성화하면 API 호출과 물리 nozzle/pulse 매핑이 맞지 않는다.
- Pi의 `sensor-lcd.service`가 USB 시리얼을 단독 소유하고 `127.0.0.1:8766` 펌프 브리지를 제공한다. 브리지 POST 성공은 **시리얼 송신 성공**이며 실제 급수량의 측정이 아니다. 실행기는 펌프 ACK/상태를 재확인하고 최대 8초 동작을 설정해 두었지만, 유량·사출구별 물리 경로는 아직 실측·확정되지 않았다. `farm_stream_gateway.py`도 존재하며 HMAC ticket claim, `/api/stream/:ticket`, `/api/snapshot/:ticket` 및 1280×720/10fps 출력은 백엔드와 정적으로 일치한다. 카메라 실제 설정·현장 접속은 확인하지 않았다.

## 2. 도메인과 데이터 계약

| 대상 | 추가/변경할 계약 | 불변 조건 |
| --- | --- | --- |
| `FarmSite` | 고정 코드 `HYDROPONIC`, `Y_FARM`; 표시 이름, 연결 게이트웨이, 운영 상태/기능 | 급수 가능 여부는 프론트 표시가 아니라 서버 정책에서 결정. 수경재배 급수 명령은 항상 거부 |
| `Order` | 선택한 `siteCode`를 주문 시점 스냅샷으로 저장 | 주문 확정 시 생성한 `Plant.siteCode`와 동일. 기존 주문은 근거 없는 자동 추측 금지 |

상품/분양 가능 상태도 사이트별로 관리한다. 같은 작물이 두 공간에 있을 수 있으므로 `productId`만으로 주문 장소를 결정하지 않는다. 사용자는 상품 또는 주문 과정에서 재배 공간을 명확히 보고, 관리자는 해당 사이트의 빈 영상 영역만 연결한다. 기존 RDK 할당 식물은 현장 근거와 DB를 대조해 수경재배로 이관하고, 카메라 미배정·출처 불명 식물/주문은 `미확인` 목록에서 관리자 승인 후 확정한다. 기존 이벤트·로그·영상 할당·급수 기록을 일괄 삭제하거나 임의로 Y-farm으로 옮기지 않는다.

## 3. 영상: 게이트웨이는 둘, 사용자 API는 하나

1. RDK 스트림 경로를 유지한 채 백엔드 내부에 `RdkStreamAdapter`와 `PiStreamAdapter`를 두고 식물의 `gatewayId`로 선택한다. 사용자 `GET /api/web/plants/:plantId`의 `streamingUrl` 및 공개 서명 티켓 프록시 경로는 동일하게 유지한다. 티켓에 `plantId`, 소유자, `siteCode`, `gatewayId`, 카메라·영역, 배정 버전을 넣고 프록시 시점에 재검증한다. Pi/RDK IP·RTSP 계정은 브라우저에 노출하지 않는다.
2. Pi 영상 서비스는 카메라 목록 설정, 카메라당 단일 RTSP 수신, 원본/영역 JPEG·MJPEG, 영역 배정·토큰, 상태/가용 영역, 비시청 시 해제 계약을 제공한다. 카메라 종류·대수·IP·실제 식물 영역은 현장 확인 전에는 예시로도 고정하지 않는다. Pi 4의 CPU·LTE 부하를 계측해 출력 해상도/FPS/동시 시청 제한을 정한다.
3. Render→Pi 영상 호출은 기존 RDK용 Tailscale 프록시를 무조건 재사용하지 않고 Pi까지 도달하는지 확인한다. 게이트웨이별 베이스 URL·인증 키·허용 호스트·타임아웃을 분리한다. 장시간 MJPEG 중계는 동시 접속/중단 처리와 단일 프레임 미리보기로 데이터 사용을 억제한다. 수경재배 4대 스트림의 기존 동작은 회귀 기준이다.

## 4. Y-farm 정량 급수: 비활성부터 시작

사용자 웹앱 → 백엔드 명령 생성 → Pi의 **아웃바운드 HTTPS** 명령 claim → Pi 단일 실행기(서보 이동, 안정화, 펌프 ON/OFF/ACK) → 백엔드 완료·실패 보고 → 급수 이력/화면 상태.

- 기존 `POST /api/web/control/water`의 요청 형태 `{plantId, volume}`(mL)는 유지하되 `Idempotency-Key`를 필수화한다. 로그인 소유권, `Y_FARM`, 유효한 Pi/사출구/펌프 배정, 장비 준비 상태, 현장 보정에 따른 1회·일일 상한과 활성 명령 중복을 서버가 검사한다. **수경재배는 UI 버튼이 없어도 서버가 409로 거부**한다. 새 명령 생성/claim은 `PI_IRRIGATION_ENABLED=true`와 별도 `PI_IRRIGATION_ARMED=true`가 모두 필요하다. 이미 DISPATCHED 된 명령의 완료·실패 보고와 active 조회는 스위치를 내려도 장치 인증키가 있으면 가능해 미결 잠금을 풀 수 있다. 응답은 즉시 급수 성공이 아니라 `commandId`와 `PENDING` 상태다. `GET /api/web/control/water/:commandId` 및 기존 `GET /api/web/water/:plantId`로 상태·성공 이력을 읽는다.
- 구현된 Pi 장치 API는 RDK 공용 키와 분리되어 `GET /api/pi/irrigation/commands/claim`, `/commands/active`, `POST /command/:id/fail`, `/water`를 제공한다. 별도 `X-Pi-Irrigation-Key`·장치 ID를 쓰며 가장 오래된 명령 한 건을 `PENDING → DISPATCHED`로 claim한다. 고유한 `activeIrrigationDeviceId` 인덱스로 Pi 하나에 활성 명령 하나만 허용하고, 완료/확정 실패는 잠금을 풀며 불확실 실패는 관리자 확인 전 잠금을 유지한다. 현재 heartbeat·lease는 구현하지 않았다. 분실된 `DISPATCHED` 작업은 자동 재전송하지 않으며 Pi agent가 기동 시 active 조회 후 실행 여부를 먼저 조정해야 한다. 완료 보고와 `Water` 생성은 `commandId` 고유 인덱스로 멱등 처리한다.
- GPIO18을 **한 서비스만** 소유하도록 수동 보정 화면과 자동 실행기를 단일 Pi 제어 서비스/작업 큐로 합치거나, 명확한 유지보수 모드로 상호 배타 전환한다. 실물 사출구 번호 `1·3~9`, Pi에 저장된 영점·오프셋·500~2500µs 펄스 프로필을 단일 보정 원본으로 사용한다. 기존 자동 실행기의 0~9 인덱스 및 1000~2000µs는 폐기/변환 검증 전 사용 금지. `nozzleNo`는 RDK 영상 `zone`과 절대로 혼용하지 않는다.
- 펌프 둘 다 OFF 확인 → 사출구 이동 → 안정화 → 지정 펌프만 ON → 시간 중 ACK/상태 확인 → OFF 확인 순서로 실행한다. 시리얼 장애, 다른 펌프 ON, 캘리브레이션 미설정, 매핑 버전 불일치, 서보 상태 불명은 fail-closed. 현재 ESP32 10초 자동 OFF를 최종 안전장치로 유지하고 실측 유량을 통한 8초 이하량만 허용한다. 프로세스 재시작·LTE 단절·OFF 미확인 시 `NEEDS_REVIEW`로 잠그고 관리자 현장 확인 전 재급수하지 않는다.
- 유량계가 없으므로 화면/DB에는 `요청량`과 `추정 토출량`을 구별하고 **실측 급수량이라고 표현하지 않는다**. 정확한 mL 보장에는 유량계 또는 계량 시험이 별도로 필요하다.

## 5. 웹앱·관리자 화면 설계

- 사용자 홈/내 식물/일기에서 `전체 | 수경재배 | Y-farm` 필터 또는 탭과 사이트 라벨을 일관되게 제공한다. 사이트는 서버의 식물·주문 데이터에서 받으며 프론트에서 작물명으로 추론하지 않는다.
- 실시간 탭은 기존 영상·기록 흐름을 공통으로 유지한다. `Y_FARM`이고 서버 `capabilities.canWater=true`인 식물에만 **기록 옆 급수** 버튼을 표시한다. 급수 바텀시트는 서버가 반환한 허용 mL 범위·최근 급수·진행 중 작업을 보여주고, 양을 입력/확인하면 중복 탭을 막는다. 요청 직후 `접수→진행→완료/실패/확인 필요`를 표시하고 성공한 이력에는 요청량·추정량·시각을 구분한다. 수경재배 식물에는 급수 버튼과 빈 급수 패널 자체를 표시하지 않는다.
- 관리자 페이지에는 전체 개요와 사이트 필터를 함께 둔다. 사이트별 식물·주문·카메라·할당/미할당·급수 상태를 한눈에 보되, 카메라 원본은 한 번에 한 대만 라이브로 재생한다. 수경재배는 기존 4대/72칸 편집을 유지한다. Y-farm은 카메라·영역 배정과 **별도** 사출구·펌프 배정/보정 상태를 보여주고 중복·불일치·미확정 매핑을 경고한다. `NEEDS_REVIEW` 해제는 현장 OFF/토출 확인 후 관리자만 가능하다.
- 주문에는 사이트를 명시하고 관리자 입금 확인 후 같은 사이트의 빈 영상 영역만 후보로 보여준다. 사이트별 상품 상태·가격이 달라질 수 있으므로 카탈로그/주문 계약도 같이 확장한다. 기존 RDK 화면을 Pi로 일괄 바꾸지 않는다.

## 6. 구현 순서와 교차검증 완료 조건

1. **데이터 감사·계약 확정:** 현재 Plant/Order/Water와 RDK 할당을 사이트별로 목록화하고 미확인 기록을 분리한다. Pi 활성 사출구·각도·펌프/식물 배치도 현장 표로 확정. 기존 DB/장비 설정 백업과 롤백 절차 작성.
2. **백엔드 사이트 모델/조회:** 두 사이트의 필터·상세·주문 계약과 사이트별 기능 플래그를 추가한다. 기존 수경재배 API·RDK 영상은 그대로 통과해야 한다. 급수 기능 플래그 기본값 OFF.
3. **Pi 단일 제어기:** 수동/자동 GPIO 소유권을 통합하고 실측 보정·펌프 ACK·watchdog·정지/재시작 복구를 가짜 장치로 검증. 현장 보정 전 자동 급수 서비스 활성화 금지.
4. **급수 명령/API:** 장치별 원자적 claim, 멱등 완료/실패·불확실 잠금, 하루/1회 상한, 사용자 이력, 관리자 확인 절차를 구현. 가짜 Pi로 동시/중복/네트워크 장애 시나리오 통과.
5. **Pi 영상 게이트웨이:** 실제 카메라 모델·IP 확인 후 인증 스트림, 단일 RTSP 리더, 배정/티켓/프록시, 영상 종료·재연결, LTE 사용량을 검증. 기존 수경재배 4개 카메라/72칸 회귀 테스트 필수.
6. **웹앱·관리자 UI:** 사이트 필터, Y-farm 전용 급수 버튼·용량 입력·명령 상태/이력, 사이트별 주문·노드·장비 상태. 수경재배 버튼 부재와 직접 API 호출 차단을 모두 테스트.
7. **단계적 현장 전환:** 펌프 전원 분리 모의 시험 → 사출구 위치·유량 소량 계량 시험 → 한 식물·한 펌프 제한 시범 → 장애/재부팅/중복 요청 시험 → 범위 확대. 각 단계 실패 시 급수 기능 플래그 OFF; 기존 RDK 스트림은 유지.

자동 테스트에는 사이트별 접근권한, 수경재배 급수 요청 거절, 잘못된 식물↔사출구 매칭, 두 식물 동시 요청의 단일 펌프/서보 직렬화, 멱등 재시도, 명령 lease·재부팅 후 불확실 상태, 중복 완료 보고, 스트림 티켓 만료·소유권·사이트 교차 접근, 기존 RDK 스트림/주문/72칸 회귀를 포함한다. 통합 테스트는 `웹앱 → 백엔드 → 모의 Pi → 명령/Water → 웹앱`과 `웹앱 → 백엔드 서명 프록시 → Pi 영상`을 각각 통과시킨다. 현장 급수·화면별 영상 품질은 코드 테스트로 대체하지 않는다.

## 7. 구현 전 필요한 현장 결정

- Y-farm 식물/주문이 각각 어떤 사이트·사출구에 속하는지에 대한 실제 배치표. 2번·10번 사출구는 현재 사용 금지이며 번호를 다시 매기지 않는다.
- Y-farm 카메라 모델·대수·IP·각 식물 영상 영역, Pi가 카메라와 같은 LAN인지, Render 프록시에서 Pi 접근 가능 여부.
- 펌프 1·2 각각의 **실측** mL/s, 사출구별 물이 실제 도착하는지, 최소 신뢰량·1회/일일 상한, 배관 잔량과 물통/호스 안전 확인 방법.
- 관리자 수동 보정이 필요한 시간대와 자동 급수 유지보수 모드 운영 방식. 실물 서보 위치 센서·유량계가 없다는 한계를 사용자 화면에 어떻게 알릴지.

위 값과 현장 시험이 없으면 Y-farm 급수는 `준비 중/미설정`으로 유지한다. 이번 점검에서도 펌프와 서보는 움직이지 않았다. Pi 코드 위치는 확인했지만 현재 급수 agent가 이전 RDK 계약을 사용해 새 backend와 미연결 상태이며, 카메라 gateway의 실제 설치/설정 및 하드웨어 연결도 검증하지 않았다. 실제 하드웨어 연동과 배포는 수행하지 않았다.
